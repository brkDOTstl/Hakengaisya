# Bounded software delivery preset

Suite version 0.8.8. Preset bounded-software revision 1.0.0. Evidence level: structurally validated with simulated control paths; real-task validation remains a 0.9 activity.

This is the first complete preset within its declared small technical scope. It combines source-backed working practices, executable graph expansion, bounded staffing, direct-supervisor acceptance, correction/recovery paths and packaged examples. It supports a small tool, script, localized change or bug fix with routine operational risk. Complexity can still require a strong model; it does not create more administrative layers.

## Select the right shape

| Variant | Actual work packets | Execution pool ceiling | Acceptance |
| --- | --- | --- | --- |
| micro | One coherent delivery, internally named handover | One currently assigned owner | Existing host as direct supervisor; every task criterion is checked |
| small-parallel | Two independent components, then one integrated delivery | Two currently assigned owners; integration reuses a qualified owner | Existing host accepts each component and the integrated result |

The two components need disjoint writes, no dependence on unfinished peer outputs, an explicit reason for parallel work and a concrete integration contract. Shared external interface specifications are allowed. A single coherent component does not receive an extra handover job. UI, design, research or specialist departments are never inferred from a title. Declare only outputs the task actually needs.

The pool limits are ceilings. Given comparable supported route observations, the planner can reuse one inexpensive adequate owner when a second context is not worth its overhead. Tighter caller limits are retained. The controller now checks the declared max_workers against current assignment bindings even without a profile-based route plan, so a separate integration owner cannot silently enlarge the pool. Replacing a failed current binding is possible after reassessment; prior owners and their results remain in history. This does not cap all historical model calls or authenticate actual contexts; the host enforces real execution and the existing dispatch/retry ceilings.

More than two streams, elevated risk, production deployment, live migrations, unresolved discovery and artistic acceptance require another reviewed workflow. A no-match result is a real scope boundary. Cross-client work uses the federation contract and actual adapter preflight; a preset does not contact another agency.

## Research and adaptation

Reviewed 2026-10-24. [The preset source record](../presets/bounded-software.json) carries the exact links, review date, adoption and transfer limits.

- [Basecamp's size adaptation](https://basecamp.com/shapeup/4.1-appendix-02) informs combining responsibilities in tiny teams and adding structure when coordination requires it.
- [Mapping scopes](https://basecamp.com/shapeup/3.3-chapter-12) informs grouping work by independently finishable results.
- [Deciding when to stop](https://basecamp.com/shapeup/3.5-chapter-14) informs scope boundaries, producer checks and bounded correction.
- [Google's review standard](https://google.github.io/eng-practices/review/reviewer/standard.html) informs evidence-based review and distinguishing necessary correction from optional polish.

The one/two-owner ceilings and direct-supervisor authority are Hakengaisya design choices. They are not copied company headcounts or proof of agent speed, cost or quality. The complete preset contract and its validator remain separate from those real-world references.

## Host workflow

The host performs the short intake and shapes coherent components from the user's request. It fills these forms; users do not have to write JSON. A component includes id, objective, task_type, difficulty, skills, exact writes, outputs, acceptance and optional external inputs/required tools. Dependency and supervisor fields are generated by the preset and cannot be injected through component input.

The request also names run_id, objective, family:bounded-software, outcome, risk:routine, lead_context, final acceptance and constraints. For small-parallel, add parallel_reason and integration. Optional workers, planning_limits, stricter runtime limits, DEI, explicitly enabled improvement and a current intake_triage record are preserved. Caller-supplied source evidence or UI requirements must be concrete, not fabricated.

```powershell
node scripts/workflow.ts presets
node scripts/workflow.ts preset-inspect bounded-software
node scripts/workflow.ts preset-validate presets/bounded-software.json
node scripts/workflow.ts preset-select examples/presets/micro.json
node scripts/workflow.ts preset-expand bounded-software examples/presets/small-parallel.json
```

Equivalent read-only MCP tools are hakengaisya_presets_list, hakengaisya_preset_inspect, hakengaisya_preset_validate, hakengaisya_preset_select and hakengaisya_preset_expand. Selection reports selected, no-match or ambiguous. Expansion returns a draft, its brief, staffing rationale, operating stages, exception paths and optional route-plan advice. It creates no run, launches no model and grants no extra permissions.

Pass the returned brief member to the existing hakengaisya_create_run tool, or save that member and use the ordinary create command. Do not pass the entire expansion response as a brief. The existing assign/start/submit/review events then operate normally. Each created run stores the preset ID, revision, selected variant and contract hash. The expanded graph, limits and acceptance are frozen in the run; later preset edits do not change them. The hash is provenance metadata, not an authentication or real-execution certificate.

The shipped runtime includes both example requests. Read-only selection/expansion and persisted run creation also pass from an unrelated directory. Tool availability and these protocol checks do not prove that a fresh AI host will automatically choose the preset.

## Readiness, evidence and correction

- With workers, use the existing route planner and inspect its qualification, trial, cost and tool findings. Explicit trial mode remains opt-in and is never relabelled as supported capability.
- Without workers, an unconstrained draft reports requires-host-qualification. The host must establish actual capability and tools; no optimized-price claim is made.
- A hard budget/deadline without route/overhead evidence reports needs-evidence and cannot be assigned through the preset run. Unknown prices, startup time or review overhead are not zero.
- A failed or unverified review returns the packet to correction and invalidates affected descendants. The new attempt needs a renewed ability-fit assignment. Unpriced host bindings may be replaced within the current pool; changes to a frozen planned route require a supervisor-reviewed replacement plan/run while retaining prior history.
- If an integration failure comes from a component, the supervisor explicitly reopens that producing component. Its accepted peers remain valid, while downstream integration waits for the corrected component's acceptance. The integration owner cannot silently repair a different component outside its declared write scope.
- A missing tool or interruption keeps work blocked. Verify the original process/context before resuming or reopening. A timeout alone is not evidence that another worker may safely start duplicate execution.
- Changed inputs within the same contract can reopen affected work. Changed acceptance, topology or production scope needs a revised brief/run. Unaffected evidence stays available; the host checks whether it is still applicable.
- At the configured retry/dispatch ceiling, stop and replan. Neither an exception note nor a preset label bypasses the controller.

Final acceptance always belongs to the root/direct supervisor and covers every user criterion. Accepted components do not accept their integration automatically. The optional evaluator records de-identified observed performance separately. Harness2 remains opt-in with its own call ceiling and unknown-cost boundaries; a preset does not start a self-improvement loop by default.

## Acceptance evidence for this increment

tests/presets.test.ts covers both completed control paths, invalid definitions, unsupported scale/risk, coupled writes/dependencies, retained failure history, a reassessed replacement, interruption, retry exhaustion, missing capability, budget evidence, pool enforcement, a cheaper adequate pool and relocated packaging. tests/mcp.test.ts exercises the registered tools and run creation over real stdio MCP. npm run inspect validates the registered preset alongside legacy reference templates.

These are structural, simulated and transport checks. There is no new live-model execution, deployed product, measured staffing speedup or production acceptance claim. The web/service, product, game and other required families remain on the 0.8 roadmap.
